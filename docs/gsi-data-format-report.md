# 国土地理院ジオイド・DEMデータ形式調査

調査日: 2026-09-26  
対象: `geoid/` の公式配布ZIP、`dem/` の代表サンプルZIP、保存済み公式API応答・取得マニフェスト

## 1. 結論

- ジオイドの全国ISGデータは、UTF-8（BOMなし、CRLF）の固定格子テキストである。ヘッダー28行の後に、北から南・西から東の順で `2101 × 1601 = 3,363,701` 点が並ぶ。緯度間隔は1分、経度間隔は1分30秒、単位はメートル、NoDataは `-9999.0000` である。
- `JPGEO2024.isg` は範囲全体に値があり、実測でNoDataは0点だった。`Hrefconv2024.isg` は基準面補正が定義された224,677点だけに値があり、それ以外の3,139,024点はNoDataだった。`JPGEO2024+Hrefconv2024.isg` も同じ有効範囲で、全有効点について `JPGEO2024 + Hrefconv2024` と一致した。
- 都道府県別ジオイドGMLはUTF-8 XMLで、1次メッシュごとに `320 × 320 = 102,400` 点、緯度7.5秒・経度11.25秒（約250m）の格子である。座標記載順は緯度・経度、値の走査順は西から東、その後北から南である。
- DEMは二重ZIPである。地方区分ZIPの中に2次メッシュ単位ZIPがあり、その中にGML XMLが入る。新しいXMLはUTF-8、2010年頃の一部DEM5はShift_JISを明示しており、値は `分類,標高` の1行1点形式である。
- DEMの数値は国土地理院の標高（正高）をメートルで表す。正の値は標高基準面より上、負の値は下である。`-9999` はNoDataであり標高として扱ってはならない。分類名だけではNoDataを確定できず、数値の `-9999` も必ず判定する必要がある。
- 全国DEMの保存済み公式API応答は275 ZIP、推定528,280,586,240 bytes（492.000 GiB）である。保存先を空き約4.42 TiBの `E:\AstroSight-GSI-data-20260926` に変更したためローカル容量は足りる。UIグリッドから先に数えた203 ZIP・約370.4 GBという値とは差があり、保存済みAPI成功応答の275件を容量計画の基準とする。

### 3.1 ZIP内部

| エントリ | 非圧縮サイズ | 役割 |
|---|---:|---|

| `Hrefconv2024.isg` | 37,003,632 | 基準面補正量 |
| `JPGEO2024+Hrefconv2024.isg` | 37,003,642 | 両者の和 |
| `geoidcalc_linux_x86_64.tar.gz` | 1,589,825 | Linux計算ツール |
| `geoidcalc_win64.exe` | 3,137,024 | Windows計算ツール |
| `input.txt` | 36 | 計算入力例 |
| `manual2024.pdf` | 1,525,941 | 付属説明書 |

### 3.2 テキスト形式とヘッダー

- 拡張子: `.isg`
- 形式: テキスト
- 文字コード: UTF-8として厳格デコード可能、BOMなし
- 改行: CRLF
- ヘッダー: 28行。`begin_of_head` から `end_of_head` まで
- 値区切り: 1個以上の空白
- データ部: 1物理行が1緯度行で、各行1,601値。全2,101行
- 小数点: `.`

3つのISGに共通する実測ヘッダーは次のとおりである。

```text
data units     : meters
data format    : grid
data ordering  : N-to-S, W-to-E
coord type     : geodetic
coord units    : dms
lat min        = 15°00'00"
lat max        = 50°00'00"
lon min        = 120°00'00"
lon max        = 160°00'00"
delta lat      = 0°01'00"
delta lon      = 0°01'30"
nrows          = 2101
ncols          = 1601
nodata         = -9999.0000
ISG format     = 2.0
```

配列インデックスを0始まりの `row`, `col` とすると、対応座標は次で求められる。

```text
latitude  = 50.0 - row * (1 / 60)
longitude = 120.0 + col * (1.5 / 60)
index     = row * 1601 + col
```

したがって、緯度・経度の入力順をデータ列が直接持つ形式ではなく、ヘッダーと行列位置から座標を復元する固定格子である。

### 3.3 実測点数・値域

| モデル | 全点数 | 有効点 | NoData | 有効値の最小 | 有効値の最大 |
|---|---:|---:|---:|---:|---:|
| `JPGEO2024` | 3,363,701 | 3,363,701 | 0 | -3.8045 m | 56.3447 m |
| `Hrefconv2024` | 3,363,701 | 224,677 | 3,139,024 | 0.0000 m | 1.3050 m |
| `JPGEO2024+Hrefconv2024` | 3,363,701 | 224,677 | 3,139,024 | 8.6939 m | 52.2631 m |

全224,677有効点を比較し、`JPGEO2024 + Hrefconv2024 - combined` の最大絶対残差は浮動小数点丸め範囲の `7.11e-15 m` だった。例えば緯度31.5°、経度140.0°では `42.2105 + 1.3050 = 43.5155 m` である。

実装上は全国の基本ジオイド高に `JPGEO2024` を使い、基準面補正が必要な用途・地点でだけ有効な `Hrefconv2024` を加える必要がある。combinedファイルを単独で全国用に使うと、大部分がNoDataになる。

ジオイド高 `N` の符号は楕円体面からジオイド面への上向きを正とする。AstroSightで国土地理院DEMの正高 `H` を楕円体高 `h` に直す関係は `h = H + N`、逆は `H = h - N` である。

## 4. 都道府県別ジオイドGML

### 4.1 ZIP内部

都道府県ZIPには以下が入る。

- `manual2024.pdf`
- `Fmdid*.xml` メタデータ
- `FG-GML-<mesh>-dghm250-2025-04-01.xml`: ジオイド高
- `FG-GML-<mesh>-hrcv250-2025-04-01.xml`: 基準面補正量。補正対象があるメッシュだけ
- `FG-GML-<mesh>-dghm250+hrcv250-2025-04-01.xml`: 和。補正対象があるメッシュだけ

東京都ZIPは50エントリ、展開後101,922,091 bytesだった。

### 4.2 XML/GML形式

- 拡張子: `.xml`
- 形式: GML 3.2系XML、ルートは `Dataset`
- 文字コード: XML宣言でUTF-8。実ファイルをUTF-8として厳格デコード可能
- 座標参照: `fguuid:jgd2024.bl`
- `<gml:lowerCorner>` と `<gml:upperCorner>`: **緯度 経度** の順、空白区切り
- `<gml:axisLabels>`: `x y`
- `<gml:sequenceRule order="+x-y">Linear</gml:sequenceRule>`
- `<gml:startPoint>`: `0 0`
- 値: `<gml:tupleList>` 内で1行1点、`種別,数値`
- XML要素がヘッダーに相当し、CSVのような列名行はない

代表の `FG-GML-5339-dghm250-2025-04-01.xml` は次の格子だった。

| 項目 | 値 |
|---|---|
| bbox | 緯度35.333333333–36.0、経度139.0–140.0 |
| grid low/high | `0 0` / `319 319` |
| 点数 | `320 × 320 = 102,400` |
| 緯度格子幅 | `0.666666667 / 320 = 約0.002083333°`（7.5秒） |
| 経度格子幅 | `1 / 320 = 0.003125°`（11.25秒） |
| 種別 | `ジオイド高` |
| 値域 | 34.5877–43.0120 m |

`+x-y` は、各行を西から東へ走査し、次の行を北側から南側へ進むことを表す。bboxはセル外周であり、幅を点数で割った値が格子幅になる。

補正メッシュの実例 `3942` は102,400点中6,400点が有効、96,000点が `データなし,-9999.0000` だった。補正量は0.5520 m、combinedの有効値は43.3923–46.5152 mだった。

## 5. 数値標高モデルGML

### 5.1 ZIPの階層

```text
地方区分・分割番号ZIP
  └─ 2次メッシュ単位ZIP
       └─ GML XML（解像度に応じて2次メッシュ全体または細分メッシュ）
```

ZIPを展開せず、`ZipArchive` で中央ディレクトリと代表XMLのストリームを読んだ。

- DEM1サンプルの `FG-GML-543754-DEM1A-20250828.zip` は36 XML、XML非圧縮合計603,271,296 bytes。
- DEM5サンプルの `FG-GML-533631-DEM5A-20250620.zip` は100 XML、XML非圧縮合計57,573,730 bytes。
- DEM10サンプルの各2次メッシュZIPは通常1 XMLだった。

### 5.2 共通XML形式

- 拡張子: `.xml`
- 文字コード: XML宣言に従う。新しいファイルはUTF-8、実測した旧DEM5BにはShift_JISがある
- 水平座標系: 更新時期により `jgd2000.bl`, `jgd2011.bl`, `jgd2024.bl` が実在する
- bbox座標順: **緯度 経度**
- 走査順: `order="+x-y"`、西から東、その後北から南
- 値: `<gml:tupleList>` 内の `分類,標高値`
- 標高単位: メートル
- NoData: 数値 `-9999`。表記は `-9999.` や `-9999.0000` などがあり得る

代表XMLの実測値は次のとおりである。

| 種類 | XML | bbox（緯度, 経度） | grid | 点数 | 角度間隔 | 値の例・値域 |
|---|---|---|---:|---:|---|---|
| DEM1A | `FG-GML-5437-54-00-DEM1A-20250828.xml` | 36.416666667–36.425, 137.5–137.5125 | 1125×750 | 843,750 | 緯度・経度とも0.04秒 | `地表面`, 2066.64–2662.12 m、NoData 1,351点 |
| DEM5A | `FG-GML-5336-31-00-DEM5A-20250620.xml` | 35.583333333–35.591666667, 136.125–136.1375 | 225×150 | 33,750 | 緯度・経度とも0.2秒 | `地表面`, 182.86–451.46 m、NoData 0点 |
| DEM10B | `FG-GML-5338-75-dem10b-20161001.xml` | 35.916666667–36.0, 138.625–138.75 | 1125×750 | 843,750 | 緯度・経度とも0.4秒 | `その他`, 907.5–2483.9 m、NoData 0点 |
| DEM10B | `FG-GML-3741-12-DEM10B-20230705.xml` | 24.75–24.833333333, 141.25–141.375 | 1125×750 | 843,750 | 緯度・経度とも0.4秒 | 有効0–170.8 m、NoData 628,155点 |

`gml:high` は最大インデックスなので、点数は `(high.x + 1) × (high.y + 1)` で計算する。bboxの幅をこの点数で割ると上表の角度間隔になる。

旧データには疎な格子もある。`FG-GML-5238-54-dem10a-20161001.xml` は格子1125×750、`startPoint=1070 0`、tupleList 274,555点で、startPointより前とtupleList終了後のセルは未記録のNoDataである。また `FG-GML-6340-37-56-DEM5B-20101001.xml` はXML宣言が `Shift_JIS` だった。変換器はXML宣言からUTF-8/Shift_JISだけを選び、置換文字を許さない厳格デコードを行う。tupleListの全非空行を検証し、未記録セル数をインベントリへ残す。

### 5.3 NoDataと水面処理への注意

実ファイルには次の両方があった。

```text
データなし,-9999.
その他,-9999.
```

したがって分類が `データなし` かどうかだけで判定すると欠測を取りこぼす。数値が `-9999` なら無条件でNoDataとする必要がある。一方、`0` は海岸・水面や標高0mの有効値になり得るため、0をNoData扱いしてはならない。

DEMの各XMLに垂直基準名の明示は見つからなかった。`srsName` は水平測地系を表し、標高値は国土地理院の標高（正高）として扱う。楕円体高が必要なAstroSight内部では地点ごとのジオイド高を加えて `h = H + N` とする。

## 6. 実装・検査で固定すべき条件

1. ISGの行列は `N-to-S, W-to-E`。緯度インデックスを南から数えない。
2. GMLのbboxは緯度・経度順だが、`x` は経度方向、`y` は緯度方向である。
3. GMLの格子幅はbbox幅を点数で割る。最大インデックスで割らない。
4. 補間セルの4隅にNoDataがある場合は、通常のバイリニア補間へそのまま入れない。
5. 全国ジオイドの基本値はNoDataのない `JPGEO2024`。基準面補正は定義域だけ加算する。
6. DEMは `-9999` を数値で判定し、0mと区別する。
7. DEMの全国データは約492 GiBなので、Workerバンドルやローカル一括展開を前提にしない。R2ではメッシュ単位に分割し、1回の全方位処理で必要ブロックをまとめて読む。
8. 1m/5m/10mでXML1件の点数と格子幅が異なる。ファイル名の解像度だけで固定寸法を決めず、`gml:high` とbboxを検証する。

## 7. 調査の再現方法

- ZIPは展開せず、.NET `System.IO.Compression.ZipArchive` でエントリを列挙した。
- コード側の `geoid/` と代表 `dem/` の公式52 ZIP（合計1,334,767,901 bytes）は中央ディレクトリを正常に開け、読取不能なZIPは0件だった。
- XML/ISGはXML宣言を検査し、UTF-8またはShift_JISの例外検出付きでデコードした（ISGとジオイドGMLはUTF-8）。
- ISGは全3,363,701点を走査し、点数、NoData数、最小・最大を集計した。
- `JPGEO2024`, `Hrefconv2024`, combinedは同一インデックスで全有効点を比較した。
- DEM代表XMLはtupleListを逐次走査し、格子点数、分類、NoData、最小・最大を確認した。
- 全国容量は `dem/gsi-dem-api-raw.json` と `dem/gsi-dem-download-manifest.json` の保存値から再集計した。
