# Work186 — Android WorkManager state hardening

Date: 2026-08-20
Base: Work185

## Purpose
Harden process-death/restart behavior without changing any image-quality
algorithm. The focus is preventing stale persisted state, hidden WorkManager
retries, and duplicate highest-quality stacks after Android stops/recreates a
worker.

## Findings in Work185
1. `status.json` could remain `running`/`queued` after Android WorkManager had
   already moved the native job to a terminal state. The registry trusted the
   persisted file and could therefore block future stacks indefinitely.
2. The background worker caught a pipeline exception, persisted `failed`, then
   returned `false`. Workmanager documents that Android uses `false` to
   reschedule/retry one-off work, creating a mismatch: UI terminal failure vs
   native retry pending.
3. Duplicate prevention existed in the Dart registry/process guard only. There
   was no second atomic unique-work guard at Android WorkManager level.
4. `pubspec.yaml` requested `workmanager: ^0.10.9`, but that version is not
   published on pub.dev as of 2026-08-20. Current stable is 0.10.7.
5. The checked-in `pubspec.lock` predates the Work183 dependency additions and
   does not contain workmanager/flutter_local_notifications. It must be
   regenerated by `flutter pub get` in a Flutter environment. The generated
   `.flutter-plugins-dependencies` file was removed so stale host-specific
   plugin paths are not handed off as authoritative.

## Implementation
- `StackJobRegistry.activeJob()` now queries `Workmanager().getWorkInfo()` when
  persisted status is queued/running.
- On Android, WorkInfo is treated as authoritative:
  - `scheduled` / `running` => keep the existing job active;
  - `succeeded` => reconcile to completed only if the Linear DNG exists,
    otherwise persist a failure explaining the missing output;
  - `failed` / `cancelled` => persist the corresponding terminal state and
    release the stale active-job block.
- WorkManager query failure is **not** treated as proof of death. The registry
  keeps the job active on uncertainty to avoid duplicate maximum-quality work.
- Added Android `onTaskStopped` handling. A stop is persisted as non-terminal
  `queued` / "一時停止・再開判定中" because WorkManager may re-enqueue stopped
  work. A later WorkInfo query decides whether it is actually terminal.
- The progress screen asks WorkManager for reconciliation when a queued/running
  heartbeat is at least 15 seconds old (normal heartbeat cadence is 10 sec).
- Home recovery performs reconciliation before displaying the saved job.
- Reporter preserves cumulative elapsed seconds and heartbeat number across a
  WorkManager task recreation; the image pipeline itself still restarts from
  the beginning because no mathematical checkpoint/resume state is claimed.
- A handled image-pipeline exception now persists `failed` and returns `true`
  to WorkManager, preventing an invisible automatic retry. Any retry is an
  explicit user action.
- New jobs use fixed WorkManager unique name `cfa-drizzle-active` with
  `ExistingWorkPolicy.keep`, plus a per-job tag and per-job output directory.
  This adds Android WorkManager's own unique-work collision guard on top of the
  persisted registry and in-process launch guard.
- After registration, WorkInfo tags are checked. If `KEEP` retained a different
  existing job, the newly-created record is not misrepresented as the running
  task.
- Corrected dependency to published `workmanager: ^0.10.7`.

## Quality impact
No image-quality path changed. Mechanical Work185-vs-Work186 comparison shows
changes only in:
- `lib/core/background/*`
- home recovery UI
- CFA Drizzle progress observer UI
- `pubspec.yaml`
- removal of generated `.flutter-plugins-dependencies`
- Work186 handoff/documentation files

No files under RAW decoding, calibration, demosaic, registration, robust
combination, CFA drizzle/reconstruction, color transform, DNG export/writer,
or native image-processing implementation were changed.

## Work187 recommended next step
Use Flutter 3.44.7 (the version pinned by repository CI), run `flutter pub get`,
commit/regenerate the lockfile, then run analyze/test/APK build. After the APK
passes, perform the real Pixel 9 Pro process-death matrix:
1. running -> app UI process killed -> worker remains running -> relaunch;
2. running -> WorkManager stop/requeue -> relaunch;
3. running -> explicit cancellation/native cancelled state -> relaunch;
4. completed while UI absent -> relaunch -> result opens;
5. pipeline failure while UI absent -> relaunch -> failure remains terminal;
6. repeated start taps/relaunch attempts -> exactly one native active worker.
