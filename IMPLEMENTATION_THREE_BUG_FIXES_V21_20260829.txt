AstroSight v21 - 3件のバグ修正
実装日: 2026-08-29
基準: AstroSight-tripod-reliability-progressive-v20-20260829.zip

対応した報告
1. 手動で被写体ピンを立てる際のメッセージが画面外に表示される
2. 被写体検索（例:「138タワー」）でピンがタワーの頂上ではなく下に立つ
3. 三脚候補点が「確定解なし」で終わることが多い（マニュアルでは候補が見つかる）

---

1. 被写体ピン操作メッセージが画面外に表示される問題

原因: src/App.css の
  .preview-load-status, .app-status { display: none; }
というルールが、廃止済みのプレビュー読込表示(.preview-load-status)と、
setSearchMessage() が書き込む一般ステータスバー(.app-status)を誤って
一緒に隠していた。.app-status にはposition指定も無く、非表示を外しても
フル画面高の3D地図<section>の後ろ（通常の文書フロー最下部）に描画され、
実質的に画面外へ押し出される状態だった。
手動被写体ピン配置（「被写体ピンを配置しました：緯度,経度」等）を含む、
setSearchMessage()を使う全ての案内がこの影響を受けていた。

修正: src/App.css
- .preview-load-status は引き続き非表示のまま（PreviewStatusコンポーネントに
  置き換え済みのため）。
- .app-status は position: fixed で画面下部（env(safe-area-inset-bottom)考慮）
  に収まる独立ルールへ分離。空文字時は .app-status:empty で非表示。

2. 被写体検索でピンがタワー頂上でなく下に立つ問題

原因: src/cesium/plateauBuildingVerification.ts の
resolvePlateauRoofGroundPoint() で、局所探索（半径20m以内）で候補が
見つからない場合の広域フォールバック（鉄塔・タワー等、半径30-50m）が、
「最も高い候補」ではなく「候補リストの中で最初に見つかった候補」
（offset→bearing順に機械的に並んだ配列の先頭）を採用していた。
双輪アーチ型の構造物（例:138タワー＝ツインアーチ138）や脚部が広がる
鉄塔では、探索半径内の交点が構造物の低い部分（脚・梁）にも生じるため、
「最初に見つかった」交点がしばしば低い位置になり、頂上ではなく構造物の
下寄りの高さが被写体ピンとして採用されていた。
さらに、広域フォールバックで見つかった候補にはStage3の精密化
（直近だけをより細かく再探索する処理）が適用されておらず、粗い8方位
サンプリングの精度のままだった。

修正: src/cesium/plateauBuildingVerification.ts
- 広域フォールバックも局所探索と同じ highestOf()（最も高い候補）を採用。
- 見つかった頂上候補の由来（局所探索/広域フォールバックいずれか）に
  関わらず、Stage3の精密化を必ず適用するよう統一。
- 探索半径・PLATEAU建物データそのもの・高さ妥当性チェック
  (MAX_PLAUSIBLE_STRUCTURE_HEIGHT_METERS等)は変更していない。

3. 三脚候補点が実在するのに「確定解なし」になる問題

前提: v19でrefineWithManualEquivalentProjection()の1次元（距離のみ）探索を
2次元（距離+方位）探索へ修正済み。今回はその上でなお残っていた原因。

原因: 同関数の格子探索が固定3パスで打ち切られ、各パス後の探索半径縮小にも
0.5m未満へは縮まない下限があった。最終判定 ROUND_TRIP_SCREEN_TOLERANCE_
PERCENT（画面比0.5%）は焦点距離に関わらず固定値だが、同じ0.5%が要求する
「実距離での位置精度」は焦点距離が長く（画角が狭く）なるほど厳しくなる。
固定3パス後の格子間隔は約1.5m前後までしか縮まらず、望遠での構図では
0.5%以内に収まる前に探索が尽きていた。人がプレビューを見ながら手動で
ピンをドラッグ調整する場合はこの格子解像度に制約されないため、同じ地点
でも手動なら見つかる、という報告内容と一致する。

修正: src/cesium/tripodCandidates.ts refineWithManualEquivalentProjection()
- パス数の固定上限を3→8（安全上限。無駄な通信を防ぐための上限であり、
  通常は下記の収束条件で先に終了する）。
- 各パスのベストスコアがROUND_TRIP_SCREEN_TOLERANCE_PERCENTの1/5以内に
  収まった時点で、それ以上格子を細かくしても最終判定が変わらないため
  早期終了する収束条件を追加（画角が広く元々精度が出やすいケースでは
  従来通り早期に終わり、DEM通信量は増えない）。
- 探索半径縮小の下限を0.5m→0.025m（格子間隔換算で約5cm）に緩和し、
  望遠構図で必要なセンチメートル単位の位置精度まで格子を縮小できるように
  した。
- CameraModel投影経路・0.5%round-trip判定・DEM解像度（1m固定）・
  収束角度条件・wide fallback・double-checkは変更していない。

追記（同日）: 4件目 — 三脚候補点が「候補点計算中」のまま止まって見える

報告された実機診断（1600mm・138タワー・09:27、太陽の交点候補1件→確定0件、
roundtrip-vertical-outside-tolerance、所要時間3.6秒）を確認した結果、
計算自体は3.6秒で完了・却下されていたにもかかわらず、地図上の候補点
ラベルは「候補点計算中」の表示のまま変化していなかった。

原因: src/cesium/celestialMap.ts のupdateTripodCandidateEntities()と
src/components/Map2DOverlay.tsx の候補ラベルが、いずれも
candidate.solutionType === "preliminary" だけを見て「計算中」表示を
出していた。v20の仕様により、精密計算が「確定解なし」「通信失敗」で
終わった天体の暫定候補（solutionTypeはpreliminaryのまま）はあえて
消さずに残す設計になっているため、計算が実際には終わっているのに
ラベルだけが「計算中」で固定されたままになっていた。ユーザーからは
「三脚候補点が表示されない（＝いつまでも出てこない）」ように見える。

修正: src/cesium/celestialMap.ts, src/App.tsx, src/components/Map2DOverlay.tsx
- updateCelestialMapEntities() / updateTripodCandidateEntities() に、
  実際に計算中かどうか（tripodCandidateCalculationStatus === "calculating"）
  を新しい引数として渡すようにした。
- solutionType==="preliminary"のラベルを、計算中は従来通り「候補点計算中」、
  計算が完了（確定解なし・失敗）した後は「概算候補（確定解なし）」と表示を
  分けた。
- Map2DOverlay.tsx にも同じ区別を持つtripodCandidatesCalculatingを追加。
- 候補データ自体（位置・座標・破棄理由等）は一切変更していない。表示文言
  のみの修正。

検証
- npm install（node_modules導入）した上で以下を実行し全てPASS:
  - npx tsc -b（型チェック込みフルビルド）
  - npm run build（Vite本番ビルド）
  - npm run test:regression（33グループ、全PASS）
  - npm run lint（エラー0、警告は既存の無関係なスクリプトのみ）

追記（同日）: 5件目 — 実機診断で判明した「探索窓の外に真の解がある」ケース

報告された2件目の実機診断（250mm・被写体まで979m、太陽の交点候補1件→
確定0件、roundtrip-vertical-outside-tolerance、方位誤差0.0011°に対し
仰角誤差0.096°・dy=-1.745%）を分析した結果、4件目までの修正（格子解像度・
パス数の緩和）では対応しきれない、別クラスの原因を確認した。

原因: refineWithManualEquivalentProjection()の探索窓（距離方向の半径。
中心距離979mに対し radialRadiusMeters = max(24, min(80, 979*0.04)) ≈ 39m）
に対し、方位誤差はほぼゼロ（0.0011°）なのに仰角誤差だけが大きく残って
いた。これは「真に仰角が一致する距離」が、粗いECEF/DEM交点から見て
探索窓（±39m）の外側にあったことを示す。この状態で毎パス必ず探索半径を
縮める（4件目までの修正後もこの挙動は残っていた）と、外縁の点を新しい
中心として採用したまま半径だけ縮んでいき、外側にある真の解に届く前に
探索が実質的に停止し、最良候補が窓の外縁付近に張り付いたまま
0.5%の許容値内に収まらず却下されていた。

修正: src/cesium/tripodCandidates.ts refineWithManualEquivalentProjection()
- 各パスの最良候補が探索格子の外縁（距離方向・横方向いずれかの端）で
  見つかった場合は、その地点を新しい中心として同じ半径のまま次のパスへ
  進む（探索窓をスライドさせる）よう変更。半径を縮めるのは、最良候補が
  外縁ではなく窓の内側で見つかったときだけに限定した。
- 上記のスライド挙動によりパス数が増えうるため、暴走防止の上限を
  8→12へ引き上げた（1パスあたり最大81点のDEM取得はバッチ・キャッシュ
  経路のため、上限を多少上げても通信コストは限定的）。
- サンドボックス環境ではCesium 3Dシーン・実地形データを動かせないため、
  この挙動をNode.js単体の数値シミュレーションで検証した（scripts化は
  未実施、手元検証のみ）。真の解が探索窓の外（250m相当）にあるケースで、
  旧ロジック（毎パス縮小）は最終スコア7.34%（許容0.5%を大幅に超過）で
  外縁付近に張り付いて収束せず、新ロジック（外縁ヒット時はスライド）は
  8パスで0.012%まで収束することを確認した。

検証
- npm install後、npx tsc -b / npm run build / npm run test:regression
  （33グループ）/ npm run lint、全てPASS（4件目までと同一の確認内容）。
- 実地形データを使う統合的な検証（実機・実際のCesium/GSI呼び出し）は
  未実施。報告いただいた2つの実機診断（138タワー・1600mm、250mm・979m）
  の場面で、今回の修正後に確定解へ到達するかどうかの再確認を推奨する。

追記（同日）: 6件目 — 東京スカイツリー検索でピンが根元に立つ（2件目の
再発）。2件目の修正（highestOf採用・Stage3精密化統一）だけでは、根本
原因が別にあるケースが残っていることが実機再現で判明した。

原因: resolvePlateauRoofGroundPoint()は国交省PLATEAUの「全国建物3Dデータ
セット（all-bldg-maxlod2-latest）」だけを頂上判定に使っている。この
データセットは建築基準法上の「建築物」を対象としており、東京スカイツリー
や138タワーのような鉄塔・展望塔は、通常の建物とは別区分のため、この
データセットに構造物そのものが収録されていないことがある。この場合、
探索半径・「最も高い候補を採用」等のアルゴリズム側をどれだけ改善しても、
そもそもクランプ対象の3D形状がシーンに存在しないため、原理的に頂上を
検出できない（2件目の修正はこの原因には対応していなかった）。

修正: 新規 src/height/osmSubjectHeightFallback.ts
- PLATEAU建物頂上合わせ込みが失敗した場合の追加フォールバックとして、
  OSM（OpenStreetMap）のheight / building:levelsタグから構造物・建物の
  高さを推定し、検索座標のDEM地面高からその高さぶん上空へ被写体ピンを
  配置する。
- 新しいAPI・Overpassクエリは追加せず、三脚探索のsite constraints判定
  向けに既に実装済みの仕組み（server/osmSiteContext.ts の
  nearbyStructures/nearbyBuildings、/api/osm-site-context、
  src/search/siteContext.ts の fetchSiteContexts）をそのまま流用した。
  東京スカイツリーの実際のOSMタグ（height=634, man_made=tower）で
  estimateHeightFromTags()が634m・surveyed（実測値）を正しく返すことを
  Node単体で確認済み。
- 検索座標から60m以内（PLATEAU側の局所探索20m＋広域フォールバック
  30-50mと同程度）にある、名前付きで高さ情報を持つ構造物・建物のうち
  最も近いものだけを採用し、無関係な別の構造物には反応しない。
- 高さはOSMコミュニティ入力の実測値/推定値であり、PLATEAU頂上合わせ込み
  （3d-picked、実表面）ほど確実ではないため、heightSourceに新しい値
  （osm-surveyed-height / osm-levels-estimate）を設け、由来を区別できる
  ようにした。
- PLATEAU・OSMいずれからも情報が得られない場合は、従来通りDEM地面高の
  まま変更しない（新たな0m代替・推測配置は行わない）。
- src/App.tsx resolveSearchSubject()（通常のスポット検索・被写体検索
  経路）と、標準モードのスポットプリセット適用経路の両方に同じ
  フォールバックを追加した。

追記（同日）: 7件目 — 東京タワー付近（都心部）の3件目の三脚探索診断で
判明した、これまでと異なる失敗パターンへの診断強化

報告された3件目の実機診断（401mm・距離217m・東京タワー付近、
roundtrip-horizontal-outside-tolerance、方位誤差0.130°・仰角誤差0.025°・
dx=1.37%・dy=-0.91%）は、これまでの2件（「僅かに閾値超過」「窓の外に
真の解」）とは異なる特徴を示していた。dx・dyの両方が閾値0.5%を大きく
超えており、単純な「あと一歩」型ではない。

このケースについて:
- 必要な補正量（方位誤差0.130°を217mで換算すると横方向約0.5m相当）は
  探索窓（半径24m、5・6件目修正後は窓外でもスライドする）に対して小さく、
  6件目までの修正が有効に働いていれば通常は収束するはずの規模である。
- したがって「探索窓が足りない」「格子が粗すぎる」という既知の原因
  （5・6件目で対応済み）とは異なる、都心部特有の要因（DEMは地表面のみを
  表しビルの屋上を表現できない、建物が密集し候補地点ごとに地盤高が
  不連続に変化する等）による可能性がある。ただしサンドボックスでは実際の
  Cesium/GSI呼び出しができず、この仮説を数値的に確認・特定できなかった。

このため、次回以降の実機診断で原因を切り分けられるよう、診断コピーの
出力を拡張した（動作・判定条件・精度は一切変更していない、診断専用の
追記）。

修正: src/cesium/tripodCandidates.ts, src/App.tsx
- refineWithManualEquivalentProjection()が実際に何パス実行したか
  （refinementPassesUsed）と、1パス目時点のスコア（firstPassScorePercent、
  dx/dyのhypot・%）・最終スコア（finalScorePercent）を記録するようにした。
- 「この検索の診断情報をコピー」の出力に、最終判定詳細の各候補ごとへ
  「精密化パス」「1パス目スコア」「最終スコア」を追加した。
- これにより次回以降の診断コピーで、(a)パス数が少ない・1パス目から
  スコアが改善していない→探索が真の解の方向へ向かえていない
  （新しい種類のバグの可能性）、(b) パス数を使い切りスコアが緩やかに
  改善しているが0.5%に届かない→都心部の候補地点密度・DEM解像度限界に
  よる真の限界、のどちらに近いかを区別できる。

検証
- npm install後、npx tsc -b / npm run build / npm run test:regression
  （33グループ）/ npm run lint、全てPASS。
- 診断専用のフィールド追加であり、候補の採否・座標・高さ計算には
  一切影響しない（reject()呼び出しへの引数追加のみ）。
